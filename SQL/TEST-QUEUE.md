## Parallel-work protocol

1. Pick a READY batch, claim it as RUNNING in TEST-RESULTS with your name/time. BUILDING means wait for publication, not permission to test a partial edit. No duplicate runners/emulators. If nothing is ready, stop and report; no polling loop or paid automation.
2. Record HEAD and SHA-256 fingerprints of the actual source/test/config inputs, **including untracked files**. Compile first if needed; fingerprint after generation and again after tests. Changed inputs → STALE, never claim current code passed. Do not commit/stash/reset/check out branches or overwrite another AI's work.
3. Write missing targeted tests, then run the batch and regressions below. One small test per meaningful contract is enough; reuse existing fixtures/helpers. Full regression once per stable batch, not after every edit. Tests must assert authorization, returned fields and stored side effects, not just happy-path HTTP success.
4. Update results with exact command, exit code/count, input fingerprint and first useful failure (no PHI/keys/codes). PASS requires all scheduled checks for that row. BLOCKED identifies the missing environment/decision. A previous 361-test pass is historical, not proof of new code.
5. Use only guarded **demo-sood-clinic/loopback** emulators and synthetic data. Never use service-account keys, real patient records, production writes, deploy/migrate, new resources/providers/backups or network installs. Request environment permissions normally if required; never bypass a denial.
6. Run SQL/Auth and Firestore/Functions emulator suites **sequentially** (shared ports). Do not regenerate SDKs while implementation is editing connector sources. Ask via a result BLOCKED row if ownership is unclear. Do not weaken source/guest release guards; expected release-check failure is a hold, not permission to ship.
