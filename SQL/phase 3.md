## Directory milestone design (before P3-07a)

This milestone moves directory reads to SQL and hardens the administrative lifecycle actor check. Existing lifecycle Firestore metadata is a temporary legacy projection until P3-07 replaces its writers; SQL is refreshed from current Auth, not from that Firestore copy. Do not claim that the entire staff lifecycle has migrated or that old Firestore tokens are immediately invalidated everywhere. Newly introduced SQL directory access requires a current live Auth check, so stale admin claims alone cannot authorize it.

No real patient data is copied. Staff data is basic account metadata already managed by this application and can be rebuilt from Auth. Disable/delete/account-role changes in Auth are projected as inactive/none, not destructive deletes in SQL. SQL reconciliation is idempotent: unchanged rows are not rewritten or re-audited.

## Recovery after an uncertain staff operation

This is an operational recovery path, not a routine command. Never delete a lock merely because it is old, and never let a scheduled expiry race an in-flight Auth change.

1. Use the IAM-only `InspectStaffAccessLock` read to obtain its request/actor IDs, then `InspectStaffAccessChange` with that exact request UUID to read the pending audit's target/action. The initial audit ID equals the request UUID; no time-based guessing is needed. Do not log private metadata. Confirm the associated Function request is finished and no staff change remains in flight. If SQL is unavailable, restore availability first; do not bypass the lock.
2. Read the affected Firebase Auth user directly using a trusted Admin SDK session. Determine the actual disabled/role/doctor/forced-password/session-cutoff state. Do not infer completion from the browser error, and do not recreate/reset a real account speculatively.
3. With the exact lock owner/request and actual user projection, invoke IAM-only `FinishStaffAccessChange` using action `staff_change_incomplete`. If Auth confirms no target account exists and no create succeeded, `AbortStaffAccessChange` can record rejection/release instead. Both verify lock ownership. Never issue raw DELETE or automatically clear another request's lock.
4. Reload the directory/activity log and review the account before issuing a new explicit action. A partial provision can leave a disabled account without completed staff claims; that needs deliberate administrator recovery, not a repeated provision/reset. No production failure or recovery was induced during these tests.
