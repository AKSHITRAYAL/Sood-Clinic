01 The short version

This is a real, working clinic management system in the middle of a large architectural migration from Firebase Firestore to Firebase Data Connect (SQL). The old system works and is deployed. The new one is largely built, well tested, and deliberately not switched over.

What works today

  • Public site — home, about, contact, health guides, patient reviews, booking, patient portal (appointments, documents, health, account, security).
  • Staff site — admin, patient directory, audit log, catalogue, feedback moderation, visit types, doctor schedule, manager workspace, video queue.
  • 57 server callables handling booking, availability, staff lifecycle, catalogue, calendar, video, feedback and the new SQL patient modules.
  • Firestore rules are default-deny with a catch-all; browser writes to appointments, schedules, clinical data and audit logs are blocked.
  • Tests are green: 288 unit/component, 250 SQL & migration, 14 Firestore rules.

What is not live yet

  • The entire SQL/Data Connect slice — 39 tables, 66 operations, 18 connectors, patient/staff/schedule/audit modules — is built locally but not mounted in any router and not deployed.
  • The SQL scheduler (Phase 6) is 15% — schema and a drafted claim/release operation exist; no booking, hold, cancel or waitlist path is exported.
  • No production migration has run. A release guard deliberately blocks deployment with three named blockers.
  • App Check, API-key restriction, custom domains, backups, staging project and notifications remain open console work.
One thing needs fixing right now An uncommitted edit to SQL/dataconnect/schema/schema.gql has swallowed two schema fields into a comment. As it stands, npm run sql:compile exits 1 with 99 schema errors. Details in Findings.

03 What the product actually is

Sood Clinic is a single-doctor gastroenterology practice in Panchkula, Haryana (Dr. Brig. A. K. Sood VSM, retired). This repository is both halves of its software.

Public website

Marketing pages, an availability-driven booking flow, health education content, patient reviews, and a patient self-service portal for appointments, video consultations, documents, health records, account details and password security.

Staff website

Role-scoped workspaces for admin (catalogue, patients, audit, feedback, visit types), doctor (schedule, calendar) and manager (front-desk workspace), plus staff account lifecycle and directory management.

The domain rules that shape everything

  • Time is IST (UTC+05:30), no DST. A shared helper (Frontend/src/lib/ist.js, functions/lib/ist.js) is used everywhere. Native browser date getters are banned for business logic because Firebase Functions run in UTC.
  • Roles come only from Firebase Auth custom claims set by the Admin SDK — never from Firestore data a browser could write, never from localStorage, never from the URL.
  • The browser is untrusted. Anything touching appointments, slots, roles, money or clinical data must go through a callable function or a tightly constrained rule.
  • PHI (patient names, phones, clinical text) never reaches logs, analytics or error reports.
  • No secrets in the repo; service-account keys and .env are gitignored.

Why two sites? Splitting public and staff into separate Hosting targets gives origin isolation: staff pages ship with X-Robots-Tag: noindex, auth sessions do not cross origins, and no staff code or string leaks into the public bundle. Cross-portal navigation therefore uses plain absolute URLs, never React routes.

Deployment posture

  • Blaze billing is active (since 9 Oct 2026). Every budget alert is set at ₹25 — an alert threshold, not a spending cap.
  • Hosting deploys are cheap and routine; rules, indexes, functions and Storage deploys require explicit scope approval.
  • Nothing about the SQL work has been deployed. All 39 local tables vs. 22 last verified deployed.
  • Three Google Calendar secrets exist in Secret Manager; values are never in the repo or notes.

The SQL-era libraries

These are the interesting ones — they implement a consistent, deliberately strict pattern:

  • sqlPatientBackend.js / sqlPatientHandlers.js — a per-request factory pattern. Every handler is composed through createSqlPatientBackend(), which layers the durable link-attempt guard on top of live Auth checks.
  • sqlPatientLinkAttempts.js — a durable rate limiter: exactly 5 admitted attempts per rolling 10 minutes per account, enforced in the database so it holds across function instances.
  • sqlWeeklyHours.js / sqlSpecialHours.js — compare-and-swap against a native revision. One writer wins; losers get a stale error. Late audit failure rolls the whole write back.
  • sqlAuditLog.js — admin-only, PHI-free, keyset pagination. Every read writes its own audit_log_viewed row in the same transaction.
  • lib/engine/* — the ported scheduler engine (units, placement, availability, visit types, references).
The recurring security pattern: SQL operations use frozen sqlPatientCallableOptions (fixed region, enforceAppCheck, bounded instances, timeout, memory) — never the looser legacy callableOptions. Handlers read role and doctor scope from live Auth claims, verify the account is active in SQL, and reject revoked, disabled, demoted or forced-password-change sessions before doing any work.

07 The data layer

This is where the real work is. The system is mid-migration from a document store to a relational schema, and the repository treats that migration as a safety-critical operation rather than a refactor.

Firestore (live today)

  • Appointments, appointment slots, doctor schedules, schedule exceptions
  • Patients, medical history, medical documents
  • Staff profiles, patient directory, audit logs, notifications, counters, rate limits
  • Clinic settings, branches, departments, doctors

Every one of these is server-write-only except a constrained owner-safe profile field set.

Access levels are explicit at the database layer. Of the 66 operations, 29 are marked NO_ACCESS — callable-only, with every browser role denied by the database itself rather than by the UI. Three are genuinely PUBLIC (GetPublicClinic, GetPublicClinicContact, GetPublicDoctorHours), one is USER-scoped, and the remaining 33 default to USER.
Exact timestamps are a first-class concern. Timestamps are stored natively (microsecond precision) and carry a separate nine-digit source-evidence field. Preparation keeps native microseconds plus the original evidence string, so a reviewer can always see exactly what the source said — and every blocker is preserved rather than smoothed over.

One rule that shapes every future writer

The Data Connect compiler supports only one query block per mutation. There is no schema-level uniqueness constraint on (doctor, date). Duplicate-date prevention therefore relies on a shared compare-and-swap against a state revision: the writer preflights, then CAS-updates; exactly one writer wins. Every future SQL closure/import writer must follow that protocol.

08 Security posture

This is the strongest part of the repository. The rules are conservative, the guards fail closed, and PHI boundaries are tested rather than assumed.

Firestore rules (firestore.rules)

  • Ends with a catch-all deny: match /{document=**} { allow read, write: if false; }
  • Browser writes denied on: appointments, appointment slots, doctor schedules, schedule exceptions, medical documents, patients, staff profiles, audit logs, notifications, counters, patient directory
  • Clinical data is doctor-scoped by doctorId claim
  • Admins can not browse clinical history (deliberate privacy decision, D-07)
  • Patient may read their own record and write only a constrained safe-profile field set

Auth model

  • Firebase Auth email/password; roles are custom claims only (admin, doctor, manager, doctor also carries doctorId)
  • Any authenticated user without a staff role is a patient
  • Staff identity lifecycle is server-owned (manageStaffAccount, directory sync)
  • Revoking a token can leave an ID token valid for up to one hour — a known boundary
  • Password policy: 8+ characters with upper, lower, digit, special. SMS MFA deliberately deferred to avoid SMS cost

Failure-mode discipline

  • Fail closed is the default everywhere: a missing endpoint, a malformed provider response, an unavailable audit insert or a permission error returns no data rather than partial data.
  • Late audit failure rolls back the write — if the audit row cannot be written, the domain write is undone too.
  • Uncertain outcomes stay uncertain. A lost acknowledgement or unknown transaction outcome is never guessed at; the same request ID must be reused, not a fresh one.
  • PHI-free by construction. Audit rows carry only id, timestamp, action, actor role/uid, resource type and resource id — never names, phones, search terms or clinical text.
  • No secret, key or plaintext export is ever written into the repository; migration artifacts are AES-256-GCM encrypted with external key custody.
Still open on the console (not code work, but blocking): App Check for both web apps, browser API-key domain restriction, Cloud Storage + storage.rules, custom domain + Auth authorized domains, Firestore PITR/scheduled backups, and a separate staging Firebase project.

09 Migration & rehearsal tooling

16 modules in SQL/migration/ plus 10 scripts in SQL/scripts/. This is the most unusual part of the codebase and deserves plain explanation.

What the tooling does

  • Pure mappers — catalogue, patient identity, clinical, appointment fields, appointment identity, hours, booking config, experience/history, registry — each turning a legacy record into a candidate row with exact timestamp preparation.
  • Protected reader — AES-256-GCM encrypted source bundles, keyed content digests, cumulative version-2 checkpoints, exclusive publication with fsync, one decision per row from index zero. Dispositions are only blocked / rejected / excluded.
  • Ownership review — inventories UID/list/path claims privately, flags ambiguity, grants zero links. It never approves ownership.
  • Reconciliation — compares source and target content, detects additions, removals, content and version drift, and reports conflicts without repairing anything.
  • Target capture — read-only snapshot of 23 domain tables with actual columns and composite keys, exact UTC microseconds, encrypted output only.
  • Branch rehearsal — atomic CAS with expected name and native version, exact timestamp evidence, audit and payload-bound receipt in one transaction, on a fixed inactive synthetic branch.

What it deliberately cannot do

  • No real importer. Preparation is not an importer.
  • No apply path, no insert/overwrite/delete of candidates.
  • No clinical operation, no file fetch, no PatientLink grant.
  • No production backup, PITR or full-restore proof.
  • No ownership inferred from contact match, UID match, snapshot match or historical actor role.
  • No fees, prices or doctor offerings inferred from current service configuration.
  • No production data in fixtures, no cloud credentials, no apply flag.
Every operation in this area reports the same thing: applied = 0, readyForApply = false, zero access grants. The tooling proves that a migration could be performed safely once the remaining gates clear — it does not perform one.

The release guard

npm run sql:release-check reads local connector, schema and generated SDK sources, makes no cloud calls, and is designed to exit 1 with three named blockers:

BlockerMeaning
SYNTHETIC_REHEARSAL_OPERATIONS_PRESENTThe rehearsal-only operations are still in the connector set and must be excluded from any production release.
SYNTHETIC_REHEARSAL_SDK_PRESENTThe generated SDK still exposes them; SDKs must be regenerated after exclusion.
GUEST_RELATION_RELEASE_REVIEW_REQUIREDThe guest Appointment.patient relation is nullable locally but non-null in production — not additive. It needs explicit DDL/API/FK deletion-behaviour review or an additive redesign.

Expected state today: exit 1. That is the pass condition. A green release-check would itself be the alarm.

What the tests actually check

  • Authorization — every role (admin, manager, doctor, patient, anonymous) is tested against every operation, including the browser-UI path.
  • Concurrency — one CAS winner per revision; 8-way concurrent link attempts commit at most five.
  • Uncertainty — lost acknowledgements and unknown outcomes are exercised, and the code must stay uncertain rather than guess.
  • Privacy — audit rows are asserted to contain no name, phone, search term or clinical text; PHI is never logged.
  • Field-level privacy — clinical, email, Auth, link and provenance fields are asserted absent from staff demographic search responses.
  • Failure atomicity — a late audit failure must roll back the domain write, the version bump and the receipt together.
  • UI races — account switch, role change, patient switch and unmount are all simulated; stale responses are dropped.
The B016 story is worth reading. Writing the missing audit-log tests found two real product defects that had been shipped locally: the audit service rejected every row with a null actorUid (so all system events were invisible), and the audit component's cursor guard applied to the first page, making "refresh from the start" impossible. Both were fixed. This is what a test suite is for.

13 Findings & risks

My own reading of the tree, beyond what the documentation claims.

Finding 1 — The schema does not currently compile BLOCKER

npm run sql:compile exits 1 with 99 schema errors, all stemming from one cause. In the uncommitted edit to SQL/dataconnect/schema/schema.gql, two fields on AppointmentUnit were merged onto the end of a # comment line:

  holdHash: String   # SHA-256 of the holdId; never the holdId itself  createdAt: Timestamp! @default(expr: "request.time")

Because they sit after the #, expiresAt and createdAt no longer exist on the type. The connector admin/scheduler-units.gql still queries expiresAt, producing 96 data-type errors, 2 filter errors and 1 query error. Separately, CalendarBlock.createdAt was folded onto the createdBy line (still parses, but the intent is lost).

Fix: restore the two fields onto their own lines. Two lines. Not fixed here because AGENTS.md requires preserving other agents' uncommitted work, and this edit appears to be an in-flight change I did not author — I am flagging it rather than silently reverting someone's work.

Finding 2 — A large amount of finished work is invisible OPPORTUNITY

Four complete, tested SQL-era pages (patient portal, staff patients, staff schedule, public doctor hours) plus 18 SQL services and 13 SQL callables exist and pass tests, yet none are reachable. The value is real; the gap is a deliberate release decision, not an oversight. The blocker is the guest relation review and the missing real-source census — not more code.

Finding 3 — The migration's hard part is still ahead RISK

The rehearsal tooling is genuinely impressive: encrypted checkpoints, one-decision-per-row dispositions, atomic CAS with receipts, ownership review that grants nothing. But it still points at synthetic data and a fixed inactive synthetic branch. The outstanding work — a trusted real source census, a retained-domain importer, database commit checkpoints, anchored history and a proven restore — is the part that carries actual risk, and none of it is automated yet.

Finding 4 — Two known limits worth stating plainly
  • Token revocation has a one-hour tail: a revoked user's ID token can stay valid until it expires. This is documented, not hidden.
  • Durability is filesystem-dependent. The protected reader's crash-safety relies on POSIX fsync semantics. Network filesystems and actual power-loss behaviour are not certified — the tests inject sync failures but never cut power.
  • Load-sensitive flakiness was observed in two intermediate full-suite runs (different tests each time, green in isolation and in both final consecutive runs). Worth watching.
Finding 5 — What is genuinely strong

Beyond the tests: the fail-closed discipline is consistent across backend, client and tooling. Unknown outcomes stay unknown. Late audit failures roll back writes. Privacy allow-lists are enforced at the payload boundary, not just the UI. The release guard is a working safety interlock — it has actually stopped a release. For a system holding patient health data, this is the correct posture, and it is worth protecting as the project grows.
